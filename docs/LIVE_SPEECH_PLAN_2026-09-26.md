# 连续听译与朗读优化计划

更新于 2026-09-26。用户要求端侧同步语音→文字翻译、改善朗读，允许将机械编码按难度交给 GPT-6 Sol / Luna。翻译始终保留离线 LLM 优先，模型随安装文件提供。

## 先说明能做到什么

本轮实现连续收音、停顿分段、逐段识别并翻译，界面明确标为试用。不是边说边逐字刷新的流式 ASR，也不是已达到实时要求的同声传译。原文先显示，译文随后追加；一句失败保留错误标记。录音期间禁止朗读，避免扬声器声音再次进入识别。

已有 0.4.0 iQOO 11 Pro 记录：约 10–13 秒音频，Qwen ASR 1.7B 调用约 22.4–38.1 秒，Whisper turbo 约 9.4–13.5 秒；包含模型加载等开销。三译文 Qwen 约 25.3–28.2 秒、HY 约 10.6–11.8 秒。这些数据足以说明当前串行大模型链路不能保证追上持续讲话，但不等于稳态纯推理基准。vivo X300 Pro 尚无数据。

## 执行阶段与验收

| 阶段 | 实施内容 | 验收与边界 |
|---|---|---|
| 1 连续听译 | 16k 单声道收音；650ms 停顿；8 秒硬分段；200ms 前导缓冲；每轮最多 120 秒；串行 ASR→LLM | 有序原文/译文，完成按钮收尾，取消/后台丢弃未完成任务，模型和目标切换取消旧会话。当前使用固定能量阈值，弱声/噪声和切词需真机检验。 |
| 1 积压保护 | 2 段等待队列 + 1 段最终保留槽；不能阻塞 AudioRecord 等推理 | 队列满立刻停止录音并提示；完成的已接收分段按序处理；不让积压无限增长。停止边界后的语音不会继续收取。 |
| 1 朗读调整 | 离线音色选择与试听；保存每语言选择；语速 0.75–1.2，默认恢复 1.0；优先匹配地区音色；超长文字自然断句 | 排除联网/未安装音色；不切坏 Unicode，不把小数当句号；模型未更换，不能声称音质已升级。 |
| 2 真机验证 | 单目标 HY/Whisper 基线与其他组合对照；四语旅行句、噪声、否定数字、快速取消、后台切换；各语音色试听 | 记录从停顿至原文、至首译文的延迟，队列停止次数、漏词/重复、峰值内存和温升。当前未连接手机，不能替代为电脑结果。 |
| 3 真正流式与独立 TTS | Qwen ASR 0.6B 原生流式移植原型；Qwen3-TTS 0.6B CustomVoice 为四语独立 TTS 的优先研究候选 | 必须先验证 Android ARM64 推理、四语输出、冷/热延迟、资源竞争与许可证，再并入默认发行版。大模型 1.7B 保留质量选项。 |

阶段 1 分工：GPT-6 Sol 实现录音分段与朗读控制；GPT-6 Luna 实现队列取消/顺序测试；主 agent 负责调研、会话状态、界面、集成审核和构建。本轮未把阶段 3 的研究候选当成已接入功能。

## 调研结论及一手来源

- [Qwen3-ASR 官方仓库](https://github.com/QwenLM/Qwen3-ASR)：0.6B/1.7B 均覆盖中英西意并支持流式/离线模型能力，但官方 Python 包的流式接口依赖 vLLM。当前应用的 llama.cpp 音频整段路径不能因为模型支持流式就自动获得流式缓存。
- [antirez 原生 C 实现](https://github.com/antirez/qwen-asr)：已有分块、编码器窗口缓存和回退稳定前缀实现，可作端侧移植候选。作者也明确说明交互流式可能比整段推理慢；其 M3 Max 测量不能当 iQOO 或天玑成绩。需要固定源码版本并单独验证，不能直接替换已测的 GGUF 路径。
- [Qwen3-TTS 官方仓库](https://github.com/QwenLM/Qwen3-TTS)：0.6B 与 1.7B 系列支持包括中英西意的十语。0.6B CustomVoice 有预设音色，但不具备 1.7B CustomVoice 表列的指令控制能力。官方低延迟宣传不能推导为 Android CPU 性能。优先评估预设音色，不需要用户录音或声音克隆。
- [sherpa Kokoro 文档](https://k2-fsa.github.io/sherpa/onnx/tts/pretrained_models/kokoro.html)：该部署页面的多语版本列为中英，v1.0 明确仅加入中英支持。不能把上游 Kokoro 的语言表误认为当前 sherpa 导出已经四语可用。
- [sherpa 意大利语 Piper 示例](https://k2-fsa.github.io/sherpa/onnx/tts/all/Italian/vits-piper-it_IT-dii-high.html)：提供另一条成熟的逐语言部署路线，但自然度须与手机现有声音盲听对比，不能因更换模型就先宣称更好。
- [MNN 官方发布](https://github.com/alibaba/MNN/releases)：有 Android TTS 与端侧加速工作；不能据其框架支持推断已覆盖本项目具体模型和全部四语，更不能把高通专有后端直接算作天玑可用。

## 后续性能优化顺序

先量出分段冷/热开销，再比较常驻 ASR+翻译所需内存与逐次释放的加载开销；只有数据支持才增加常驻策略。真正流式需要稳定/临时字幕分离与上下文边界处理，不能每新增一个字就重跑整段 LLM 翻译。独立 TTS 需先生成四语样音，再测手机首包延迟和播放速度。全部离线，继续保持应用无 Internet 权限。
